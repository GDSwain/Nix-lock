#+TITLE: Nix-Lock
#+AUTHOR: Oggie
#+DESCRIPTION: A release management workflow for immutable NixOS system closures.
#+STARTUP: showeverything
#+OPTIONS: toc:2

* Project Overview

Nix-Lock is a release management workflow for NixOS.

Rather than immediately deploying every newly built operating system,
Nix-Lock intentionally separates the act of building a system from the
act of deploying it.

A candidate operating system is built, preserved unchanged, observed for
a configurable period, and only then intentionally deployed.

The objective is not to delay updates indiscriminately.

The objective is to separate build time from deployment time while
preserving the normal NixOS administration workflow.

* Core Principle

Nix-Lock treats immutable NixOS system closures as release artifacts
rather than immediate deployment targets.

Building a system produces an immutable operating system artifact.

Deployment is a separate decision.

During an observation period the candidate remains unchanged while the
user continues using the computer normally.

After the observation period expires, that exact system closure is
deployed.

Nix-Lock introduces no new deployment mechanism.

Instead, it coordinates deployment using mechanisms already provided by
NixOS.

* Background

The project originated from an investigation into whether the age of a
NixOS channel could be used as a deployment timer.

The original hypothesis was that waiting until a channel had existed for
a defined period would reduce the likelihood of deploying problematic
updates.

Investigation demonstrated that this approach was fundamentally flawed.

Channel age describes only the current head of the channel.

Whenever a newer revision is promoted the timer resets.

It therefore cannot measure the maturity of any specific operating
system.

Although unsuccessful, this investigation identified the wrong problem
and ultimately led to a better understanding of how NixOS performs
deployment.

* Fundamental Observation

Experimental investigation demonstrated that the deployable object in
NixOS is not the configuration.

The deployable object is the immutable system closure.

Configuration describes how to build a system.

A system closure is the finished operating system.

Deployment therefore concerns selecting an already-built operating
system rather than rebuilding configuration.

This distinction forms the conceptual foundation of Nix-Lock.

* Experimental Findings

The investigation established that NixOS separates three distinct
concepts.

- Editable configuration.
- Immutable system closures.
- Running operating systems.

Their relationship is approximately:

#+begin_example
Configuration

↓

Build

↓

Immutable system closure

↓

Boot / Switch

↓

Running operating system
#+end_example

The running operating system is determined entirely by the activated
system closure.

The current contents of =/etc/nixos= are irrelevant until another rebuild
occurs.

* Problem Statement

Traditional update workflows answer the question:

#+begin_quote
"What is the newest revision available today?"
#+end_quote

Nix-Lock instead asks:

#+begin_quote
"Which previously-built operating system has completed its observation
period?"
#+end_quote

These are fundamentally different questions.

Nix-Lock concerns deployment scheduling rather than update discovery.

* Project Aim

Build an immutable NixOS system closure.

Preserve that closure unchanged.

Continue using the computer normally.

Deploy that exact closure after a configurable observation period.

Repeat.

* Architectural Simplification

Early designs assumed that Nix-Lock would need to maintain its own
repository of deployment candidates.

Experimental implementation demonstrated that this assumption was
incorrect.

Nix already stores immutable system closures.

Nix already assigns stable identities to those closures.

Nix already manages garbage collection.

The only responsibility remaining for Nix-Lock is to identify which
existing closure should be deliberately retained.

Rather than introducing its own storage mechanism, Nix-Lock now owns
exactly one persistent garbage collection root.

#+begin_example
~/.local/state/nix-lock/candidate
#+end_example

This root simultaneously:

- identifies the current Candidate
- protects the Candidate from garbage collection
- provides a stable inspection point

The implementation therefore became substantially smaller than originally
anticipated.

Rather than replacing existing Nix behaviour, Nix-Lock now relies almost
entirely upon it.

This simplification represents the largest architectural change made
during development.

* Experimental Validation

The following behaviour has been demonstrated experimentally.

- Systems can be built without activation.
- Building does not modify the running system.
- System closures possess stable immutable identities.
- Identical inputs reproduce identical system closures.
- Previously-built closures remain deployable.
- A previously-built closure can be selected as the next boot target.
- A system closure can be deliberately preserved using a persistent GC root.
- The running system depends on the selected closure rather than the current configuration files.
- Rebuilding from the current configuration restores the system described by that configuration.

These observations demonstrate that the deployment mechanism required by Nix-Lock already exists within standard NixOS.

* Design Principles

- Simplicity before features.
- Policy before implementation.
- Preserve existing NixOS workflows wherever possible.
- Require the minimum practical migration.
- Introduce no unnecessary complexity.
- Prefer existing NixOS mechanisms over custom solutions.
- Separate building from deployment.
- Preserve immutable deployment candidates.
- Verify assumptions experimentally whenever possible.

* Scope

Nix-Lock is responsible for:

** Building deployment candidates.
** Recording immutable system closures.
** Preserving deployment candidates.
** Separating build time from deployment time.
** Supporting configurable observation periods.
** Deploying previously-built system closures.
** Preserving reproducibility.

* Non-Goals

Nix-Lock is not intended to:

** Replace NixOS generations.
** Replace backups.
** Snapshot user data.
** Restore complete machine state.
** Predict whether updates are safe.
** Test packages.
** Replace Git.
** Replace existing NixOS tooling.
** Require Home Manager.
** Require users to redesign existing modular NixOS configurations.

* Guiding Philosophy

Nix-Lock is not an update manager.

It is a release management workflow.

Its purpose is simply to determine when a previously-built immutable
operating system should become the running system.

Everything else remains ordinary NixOS administration.

* Terminology

** Configuration

Editable NixOS source describing a future operating system.

** System Closure

An immutable deployable operating system stored within the Nix store.

** Candidate

A Candidate is a previously-built immutable NixOS system closure that
Nix-Lock has deliberately retained for future deployment.

Conceptually, a Candidate consists of:

- one immutable system closure
- one persistent GC root identifying that closure

The closure itself remains the authoritative object.

Metadata may be associated with a Candidate in future implementations,
but it is secondary to the immutable closure.

** Observation Period

The period between building a candidate and deploying it.

** Deployment

Selecting and activating a previously-built system closure.

** Current

The system closure presently running.

** Latest

The newest configuration currently available for building.

* Initial Command: Build

The first implemented command should be:

#+begin_src sh
nix-lock build
#+end_src

The command should:

1. Build the current NixOS configuration without activating it.
2. Obtain the resulting immutable system closure.
3. Create a persistent GC root identifying that closure.
4. Verify that the retained closure is a valid NixOS system.
5. Report the retained Candidate.

The command must not alter the currently running system.

The command should use existing NixOS build mechanisms rather than
introducing a separate build process.

* Conceptual Workflow

1. Build a candidate system closure.
2. Preserve the candidate.
3. Continue normal use of the computer.
4. Allow the candidate to remain under observation.
5. Deploy the candidate.
6. Build the next candidate.
7. Repeat.

* User Experience

Normal day-to-day use of the computer should remain unchanged.

Users continue editing documents, writing software, browsing the web,
and maintaining their systems exactly as they do today.

Only the timing of operating system deployment changes.

Mutable user data continues evolving naturally throughout the observation
period.

* Current Status

The project has completed its first implementation milestone.

* Nix-Lock can now:

** Build immutable deployment candidates.
** Preserve candidates using persistent GC roots.
** Inspect retained candidates.
** Safely replace previously retained candidates.

The implementation is now intentionally entering an operational phase.

The retained Candidate will remain untouched while the computer
continues through ordinary daily use.

The purpose of this experiment is to demonstrate that a deliberately
retained immutable system closure survives normal system evolution and
remains deployable after an extended observation period.

Activation of the retained Candidate will become the next implementation
milestone.

* Success Criteria

The project will be considered successful if it can:

** Build immutable deployment candidates.
** Deploy previously-built candidates.
** Preserve reproducibility.
** Require only minimal changes to existing NixOS workflows.
** Avoid increasing day-to-day operational complexity.
** Feel like ordinary NixOS administration with one additional concept: delayed deployment.

* Implementation Principles

Implementation details are intentionally secondary.

The implementation should satisfy the project requirements rather than
define them.

The simplest implementation that faithfully satisfies the project
objectives should always be preferred.

Whenever implementation becomes simpler by relying on an existing Nix
mechanism, that approach should be preferred over introducing new
abstractions.

* Proof of Concept

The initial implementation should remain manual.

The objective is to validate the workflow rather than automate it.

Automation should only be considered after sufficient operational
evidence has been collected.

Experimental investigation has demonstrated that the required deployment
mechanism already exists within standard NixOS.

The current phase of the project extends that validation by proving that
retained Candidates survive ordinary system use before being deployed.

* Project Statement

Nix-Lock is a release management workflow for NixOS.

It treats immutable NixOS system closures as release artifacts rather than immediate deployment targets.

Candidate operating systems are built once, preserved unchanged, observed for a configurable period, and intentionally deployed later.

Nix-Lock introduces no new deployment mechanism.

It provides policy around *when* immutable operating system artifacts should be deployed while relying entirely upon the deployment mechanisms already present within NixOS.
