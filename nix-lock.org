#+TITLE: Nix-Lock
#+AUTHOR: Oggie
#+DESCRIPTION: A release management workflow for immutable NixOS system closures.
#+STARTUP: showeverything
#+OPTIONS: toc:2

* Project Overview

Nix-Lock is a release management workflow for NixOS.

Rather than immediately deploying every newly built operating system,
Nix-Lock intentionally separates the act of building a system from the
act of deploying it.

A candidate operating system is built, preserved unchanged, allowed to
complete an observation period, and only then intentionally deployed.

The objective is not to delay updates indiscriminately.

The objective is to separate build time from deployment time while
preserving the normal NixOS administration workflow.

* Core Principle

Nix-Lock treats immutable NixOS system closures as release artifacts
rather than immediate deployment targets.

Building a system produces an immutable operating system artifact.

Deployment is a separate decision.

During an observation period the candidate remains unchanged while the
user continues using and maintaining the computer normally.

After the chosen observation period, that exact system closure can be
deployed.

Nix-Lock introduces no new deployment mechanism.

Instead, it coordinates deployment using mechanisms already provided by
NixOS.

* Background

The project originated from an investigation into whether the age of a
NixOS channel could be used as a deployment timer.

The original hypothesis was that waiting until a channel had existed for
a defined period would reduce the likelihood of deploying problematic
updates.

Investigation demonstrated that this approach was fundamentally flawed.

Channel age describes only the current head of the channel.

Whenever a newer revision is promoted the timer resets.

It therefore cannot measure the maturity of any specific operating
system revision.

Although unsuccessful, this investigation identified the wrong problem
and ultimately led to a better understanding of how NixOS performs
deployment.

The failed hypothesis was useful because it changed the question from:

#+begin_quote
"How old is the current channel?"
#+end_quote

to:

#+begin_quote
"What is the actual object being deployed?"
#+end_quote

That question led directly to immutable NixOS system closures and the
current Nix-Lock design.

* Fundamental Observation

Experimental investigation demonstrated that the deployable object in
NixOS is not the configuration.

The deployable object is the immutable system closure.

Configuration describes how to build a system.

A system closure is the finished operating system.

Deployment therefore concerns selecting an already-built operating
system rather than rebuilding configuration.

This distinction forms the conceptual foundation of Nix-Lock.

* Experimental Findings

The investigation established that NixOS separates three distinct
concepts.

* Editable configuration.
* Immutable system closures.
* Running operating systems.

Their relationship is approximately:

#+begin_example
Configuration

↓

Build

↓

Immutable system closure

↓

Boot / Switch

↓

Running operating system
#+end_example

The running operating system is determined by the activated system
closure.

The current contents of =/etc/nixos= do not change the running system
until another build and activation occurs.

This separation allows a system closure to be built at one point in time
and intentionally deployed at another.

* Problem Statement

Traditional update workflows answer the question:

#+begin_quote
"What is the newest revision available today?"
#+end_quote

Nix-Lock instead asks:

#+begin_quote
"Which previously-built operating system has completed its observation
period?"
#+end_quote

These are fundamentally different questions.

Nix-Lock concerns deployment scheduling rather than update discovery.

* Project Aim

Build an immutable NixOS system closure.

Preserve that closure unchanged.

Continue using and maintaining the computer normally.

Allow time to pass while evidence accumulates around the captured
revision.

Deploy that exact closure when the chosen observation period has
completed.

Capture the next candidate.

Repeat.

* Architectural Simplification

Early designs assumed that Nix-Lock would need to maintain its own
repository of deployment candidates.

Experimental implementation demonstrated that this assumption was
incorrect.

Nix already stores immutable system closures.

Nix already assigns stable identities to those closures.

Nix already manages garbage collection.

The only responsibility remaining for Nix-Lock is to identify which
existing closure should be deliberately retained.

Rather than introducing its own storage mechanism, Nix-Lock owns
exactly one persistent garbage collection root.

#+begin_example
~/.local/state/nix-lock/candidate
#+end_example

This root simultaneously:

* identifies the current Candidate
* protects the Candidate from garbage collection
* provides a stable inspection point

The implementation therefore became substantially smaller than originally
anticipated.

Rather than replacing existing Nix behaviour, Nix-Lock now relies almost
entirely upon it.

This simplification represents the largest architectural change made
during development.

* Experimental Validation

The following behaviour has been demonstrated experimentally.

* Systems can be built without activation.
* Building does not modify the running system.
* System closures possess stable immutable identities.
* Identical inputs reproduce identical system closures.
* Previously-built closures remain deployable.
* A previously-built closure can be selected as the next boot target.
* A system closure can be deliberately preserved using a persistent GC root.
* A retained closure survives subsequent ordinary system use and evolution.
* The running system depends on the selected closure rather than the current configuration files.
* A retained closure can later be activated directly without rebuilding it.
* After activation, =/run/current-system= resolves to the deployed retained closure.
* Rebuilding from the current configuration restores the system described by that configuration.

These observations demonstrate that the deployment mechanism required by
Nix-Lock already exists within standard NixOS.

The first complete operational experiment additionally demonstrated that
the separation between capture and deployment remains valid across an
extended real-world observation period.

* Design Principles

- Simplicity before features.
- Policy before implementation.
- Preserve existing NixOS workflows wherever possible.
- Require the minimum practical migration.
- Introduce no unnecessary complexity.
- Prefer existing NixOS mechanisms over custom solutions.
- Separate building from deployment.
- Preserve immutable deployment candidates.
- Verify assumptions experimentally whenever possible.
- Preserve failed investigations when they explain architectural decisions.
- Add automation only when operational evidence demonstrates a need.

* Scope

Nix-Lock is responsible for:

** Building deployment candidates.
** Identifying immutable system closures.
** Preserving deployment candidates.
** Inspecting retained candidates.
** Separating build time from deployment time.
** Allowing observation periods to be determined by deployment policy.
** Deploying previously-built system closures.
** Verifying successful activation.
** Preserving reproducibility.

* Non-Goals

Nix-Lock is not intended to:

** Replace NixOS generations.
** Replace backups.
** Snapshot user data.
** Restore complete machine state.
** Predict whether updates are safe.
** Test packages.
** Replace Git.
** Replace existing NixOS tooling.
** Require Home Manager.
** Require users to redesign existing modular NixOS configurations.
** Decide how long an observation period should be.

* Guiding Philosophy

Nix-Lock is not an update manager.

It is a release management workflow.

Its purpose is simply to determine when a previously-built immutable
operating system should become the running system.

Everything else remains ordinary NixOS administration.

The implementation should remain as small as the policy permits.

Where Nix already provides the required mechanism, Nix-Lock should
coordinate that mechanism rather than replace it.

* Terminology

** Configuration

Editable NixOS source describing a future operating system.

** System Closure

An immutable deployable operating system stored within the Nix store.

** Candidate

A Candidate is a previously-built immutable NixOS system closure that
Nix-Lock has deliberately retained for future deployment.

Conceptually, a Candidate consists of:

* one immutable system closure
* one persistent GC root identifying that closure

The closure itself remains the authoritative object.

Metadata may be associated with a Candidate in future implementations,
but it is secondary to the immutable closure.

** Observation Period

The period between capturing a Candidate and deploying it.

Nix-Lock does not currently determine the duration of this period.

Its duration is a matter of deployment policy.

** Deployment

Selecting and activating a previously-built retained system closure.

Deployment does not require rebuilding the Candidate from current
configuration or current package sources.

** Current

The system closure presently running.

** Latest

The newest configuration or package revision currently available for
building.

* Command Evolution

The initial design proposed a command named:

#+begin_src sh
nix-lock build
#+end_src

Its intended responsibility was to build the current configuration
without activation and retain the resulting system closure.

Implementation clarified that the operation represented more than a
normal build.

The important action was the creation of a deliberately retained
deployment Candidate.

The implemented command therefore became:

#+begin_src sh
python3 nix_lock.py capture
#+end_src

The current proof-of-concept interface is:

#+begin_example
python3 nix_lock.py {capture|status|deploy}
#+end_example

This evolution reflects a broader architectural lesson from the project:
command names should describe Nix-Lock policy rather than duplicate the
terminology of the underlying Nix mechanisms.

* Current Commands

** Capture

#+begin_src sh
python3 nix_lock.py capture
#+end_src

The command:

1. Builds the current NixOS configuration without activating it.
2. Resolves the resulting immutable system closure.
3. Verifies that the result is a valid NixOS system closure.
4. Protects the new closure before altering the existing Candidate.
5. Creates the stable Nix-Lock garbage-collection root.
6. Releases Nix-Lock's reference to the previous Candidate.
7. Removes the temporary build result link.
8. Reports the newly retained Candidate.

The command does not alter the currently running system.

** Status

#+begin_src sh
python3 nix_lock.py status
#+end_src

The command reports the retained Candidate and verifies:

* the store path is present
* garbage-collection protection is present
* the retained path is a valid NixOS system closure

** Deploy

#+begin_src sh
python3 nix_lock.py deploy
#+end_src

The command:

1. Resolves the retained Candidate through the Nix-Lock GC root.
2. Verifies that the Candidate contains the NixOS activation program.
3. Identifies the currently running system.
4. Activates the retained Candidate using its own
   =switch-to-configuration= program.
5. Verifies that =/run/current-system= resolves to the Candidate after
   activation.

The command does not rebuild the Candidate.

This is important.

Deployment selects the immutable operating system that was captured
earlier rather than attempting to reproduce it from today's
configuration or package sources.

* Conceptual Workflow

1. Capture a candidate system closure.
2. Preserve the Candidate.
3. Continue normal use and maintenance of the computer.
4. Allow the Candidate to remain unchanged during its observation period.
5. Verify the Candidate.
6. Deploy the exact retained Candidate.
7. Capture the next Candidate.
8. Repeat.

Or, more simply:

#+begin_example
Capture → Observe → Deploy → Repeat
#+end_example

* User Experience

Normal day-to-day use of the computer should remain unchanged.

Users continue editing documents, writing software, browsing the web,
and maintaining their systems exactly as they do today.

System configuration may continue to evolve during the observation
period.

Mutable user data continues evolving naturally.

Only the timing of operating system deployment changes.

The retained Candidate remains fixed while the environment around it
continues to change.

* First Complete Operational Experiment

The first complete Nix-Lock deployment cycle began on August 1, 2026.

The retained Candidate was:

#+begin_example
/nix/store/hg414yf21h392z8ik8yb1x1n29szak2w-nixos-system-nixos-26.05.6200.8623c4c20aa4
#+end_example

The Candidate was protected by:

#+begin_example
/home/oggy/.local/state/nix-lock/candidate
#+end_example

The Candidate was then deliberately left untouched.

During the following weeks the computer continued through ordinary use,
configuration changes, package changes, rebuilds, and maintenance.

The original plan called for a two-week observation period.

In practice, almost four weeks elapsed before deployment, providing a
stronger test of the retention mechanism than originally planned.

At the end of the observation period, Nix-Lock reported:

#+begin_example
Locked candidate
Closure: /nix/store/hg414yf21h392z8ik8yb1x1n29szak2w-nixos-system-nixos-26.05.6200.8623c4c20aa4
GC root: /home/oggy/.local/state/nix-lock/candidate
Store path: present
GC protection: present
NixOS system closure: valid
#+end_example

The Candidate had therefore survived the observation period unchanged
and remained protected and deployable.

The =deploy= command was then implemented and the retained Candidate was
activated directly.

Nix-Lock reported:

#+begin_example
Candidate deployed
Active system: /nix/store/hg414yf21h392z8ik8yb1x1n29szak2w-nixos-system-nixos-26.05.6200.8623c4c20aa4
#+end_example

Independent verification using:

#+begin_src sh
readlink -f /run/current-system
#+end_src

returned:

#+begin_example
/nix/store/hg414yf21h392z8ik8yb1x1n29szak2w-nixos-system-nixos-26.05.6200.8623c4c20aa4
#+end_example

The exact system closure captured almost four weeks earlier had become
the running operating system.

No reconstruction from the current configuration was required.

No reconstruction from current package sources was required.

The experiment therefore demonstrated the complete workflow:

#+begin_example
Capture → Observe → Deploy
#+end_example

A new Candidate was subsequently captured, beginning the next
observation cycle.

* Current Status

The central Nix-Lock hypothesis has now been demonstrated operationally.

Nix-Lock can:

** Build immutable deployment candidates without activation.
** Preserve Candidates using persistent GC roots.
** Inspect and validate retained Candidates.
** Safely replace previously retained Candidates.
** Retain a Candidate while the surrounding system continues to evolve.
** Deploy the exact previously captured Candidate without rebuilding it.
** Verify that the deployed Candidate became the running system.
** Capture a new Candidate for the following deployment cycle.

The project has therefore progressed beyond proving whether the basic
mechanism works.

The current phase is repeated operational use.

Each subsequent cycle provides additional evidence about the simplicity,
reliability, and practical limitations of the workflow.

* Success Criteria

The original success criteria were:

** Build immutable deployment candidates.
** Deploy previously-built candidates.
** Preserve reproducibility.
** Require only minimal changes to existing NixOS workflows.
** Avoid increasing day-to-day operational complexity.
** Feel like ordinary NixOS administration with one additional concept: delayed deployment.

The first complete operational cycle satisfies the core mechanical
criteria.

Longer-term operational use remains useful for determining whether the
workflow continues to satisfy the simplicity and usability criteria over
time.

* Implementation Principles

Implementation details are intentionally secondary.

The implementation should satisfy the project requirements rather than
define them.

The simplest implementation that faithfully satisfies the project
objectives should always be preferred.

Whenever implementation becomes simpler by relying on an existing Nix
mechanism, that approach should be preferred over introducing new
abstractions.

The current implementation deliberately remains small.

Nix owns the system closures.

Nix owns the store.

Nix owns garbage collection.

NixOS owns system activation.

Nix-Lock owns the policy decision and one persistent reference to the
Candidate selected for future deployment.

* Proof of Concept

The initial implementation was intentionally manual.

The objective was to validate the workflow rather than automate it.

That proof of concept has now completed a full real-world deployment
cycle.

The retained Candidate survived an extended observation period and was
subsequently activated as the running operating system.

The experiment therefore confirmed that the required mechanisms already
present within standard NixOS are sufficient for the central Nix-Lock
workflow.

The next question is no longer whether the mechanism works.

The question is whether repeated operational use reveals a genuine need
for additional functionality.

Automation should only be introduced when such a need is demonstrated.

The project should be abandoned or redesigned if achieving its
objectives requires unnecessary complexity or significantly alters the
normal NixOS administration workflow.

The simplest implementation that faithfully satisfies the project's
objectives should always be preferred.

The successful first operational cycle does not remove this criterion.

Future development should continue to be judged against it.

* Project Statement

Nix-Lock is a release management workflow for NixOS.

It treats immutable NixOS system closures as release artifacts rather
than immediate deployment targets.

Candidate operating systems are built once, preserved unchanged, allowed
to complete an observation period, and intentionally deployed later.

Nix-Lock introduces no new deployment mechanism.

It provides policy around *when* immutable operating system artifacts
should be deployed while relying upon the deployment mechanisms already
present within NixOS.

The first complete operational experiment demonstrated that a Candidate
can be captured, retained while the surrounding system evolves, and
later deployed as the exact operating system originally preserved.

The implementation remains deliberately small because Nix already
provides almost everything the workflow requires.
